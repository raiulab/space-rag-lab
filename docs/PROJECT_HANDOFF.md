# Space Research RAG Lab プロジェクト引き継ぎ書

最終更新: 2026-10-06

この文書は、旧スレッドで行った検討・実装・検証を、新しいCodexプロジェクトの新しいスレッドへ引き継ぐための永続的なコンテキストである。新しいスレッドは会話履歴を知っていると仮定せず、この文書、`AGENTS.md`、`README.md`、`docs/LABS.md`、実際のコードとテストを情報源として扱うこと。

## 1. プロジェクトの目的

Embedding生成、ベクトル検索、RAGパイプライン、LLM API連携、検索・要約・質問応答、評価、プロンプト設計、AWS配置を、順番に手を動かしながら習得できる実習ツールを作る。

単に完成したAIアプリを配布するのではなく、学習者が次のサイクルを経験できることを目的とする。

1. 文書やコードを観察する。
2. 小さな課題を実行する。
3. 出力や評価値を確認する。
4. 失敗の原因を分類する。
5. 変更の仮説を立てる。
6. 実装して同じ評価を再実行する。
7. 改善と副作用を記録する。

最終的には、研究文書・技術報告書を扱うRAG開発に必要な一連の作業を、ポートフォリオとして説明できる状態を目指す。

## 2. 想定利用者

基本対象者は、Pythonの基本文法、関数、リスト・辞書、ファイル操作の基礎を理解し、ターミナルと仮想環境を手順に沿って扱える大学生・社会人である。

- RAG、Embedding、ベクトル検索、LLM API、画像機械学習、AWSは未経験または初級でよい。
- 割合、平均、正解率の意味を読めればよく、専門的な統計知識は前提にしない。
- クラス、型ヒント、JSONL、テスト、検索評価指標は実習内で段階的に学べる。
- 生成AIエンジニアへの転職・職種転換を考えている人も想定する。
- Notebook上の実験だけでなく、CLI、テスト、API、AWSまで経験したい人を想定する。

Pythonを一度も書いたことがない利用者は現行本編の基本対象に含めず、「Python未経験者もそのまま参加可能」とは案内しない。将来、Python、ターミナル、仮想環境、JSON、テストの基礎を扱う任意のPre-Labを追加して参加経路を用意する。

LangGraphは現行の8 Labの学習範囲外である。将来、エージェントの状態遷移や複数段階ワークフローを扱う場合は、別の発展Labとして設計する。

説明は初学者にも読みやすくするが、成果物の構造や評価方法は実務へ接続できるものにする。

## 3. これまでの検討経緯

当初はFinAgentBench、AgentEval、WattBotのような既存タスクも候補になった。しかし、既存ベンチマークは規模や前提知識が大きく、画像解析中心の宇宙データも目的とずれていた。

ユーザーの希望は次のように整理された。

- 画像より、文書の生データを扱いたい。
- 数学的な考え方も含めたい。
- 最初のプロジェクトはもう少し簡単にしたい。
- 高校生でも面白い宇宙テーマにしたい。
- Notebookだけで完結せず、実務に近いコード構成にしたい。
- Embedding、検索、RAG、評価、プロンプト、AWSを一続きで経験したい。

このため、外部の大型コンペをそのまま使わず、架空の宇宙技術報告書を使う小規模な独自RAG教材を作成した。

## 4. 決定済みの方針

### 4.1 教材テーマ

宇宙技術に関する架空の技術文書を検索・要約・質問応答する「Space Research RAG Lab」とする。

現在の文書テーマ:

- 月面観測装置の熱制御
- 火星気象観測ステーションの電力運用
- エウロパ探査機の通信・耐放射線
- 宇宙ミッション文書検索サービスの運用基準

組織名、数値、ミッションは学習用の架空データであり、実在の宇宙計画には使用しない。

### 4.2 実習形式

- Notebookは必須にしない。
- Pythonモジュール、CLI、テスト、JSON評価レポートを中心にする。
- 最初から正解を完成させすぎず、再現可能な失敗を改善課題として残す。
- APIキーなし、ネットワークなしでもLab 1〜3、5、6の主要部分を試せるようにする。
- 外部LLMは交換可能な部品とし、現在はAmazon Bedrockを任意統合として用意する。
- 学習者自身が変更前後を同じ質問セットで評価する。

### 4.3 配布と実行

- GitHubで公開できる実習ツールを目指す。
- 実習そのものは各利用者のローカルPCで行う。
- GitHub Pagesでのガイド公開は可能だが、必須要件ではない。
- ガイドをホストすることよりも、ローカルで手順、結果、問題点、次の行動を分かりやすく案内できることを優先する。
- サーバー上で利用者のコードを実行する中央集約型サービスは、現段階の対象外とする。

### 4.4 新しく明確になった製品方針

次の開発段階では、現在のCLI教材を「ローカル学習ナビゲーションアプリ」へ発展させる。

このアプリの役割は、答えを自動的に実装することではない。学習者を次の流れへ誘導することである。

```text
今日のLabを選ぶ
    ↓
学習目標と前提を確認する
    ↓
実行するコマンドと観察点を示す
    ↓
学習者がローカルで実行する
    ↓
結果を取り込み、期待値と比較する
    ↓
問題を「環境・データ・検索・生成・評価」に分類する
    ↓
段階的なヒントを示す
    ↓
再実行し、変更前後を比較する
    ↓
学習記録と成果物を保存する
```

この時点ではUIがWebブラウザであるか、デスクトップ風のローカルアプリであるかは未決定だった。現在の決定は次節を参照する。重要な要件は、利用者のPC内で動き、プロジェクトのファイル・コマンド・評価結果と安全に連携できることである。

### 4.5 ローカル学習アプリの初期方式決定

2026-09-30に、初期プロトタイプの方式とデータ対応範囲を次のように決定した。

- UIはStreamlitによるローカルWebアプリとする。
- 既存CLIとコア依存なしの学習経路を維持し、UIとPDF機能は任意extraに分離する。
- 最初はLab 1だけを対象にする。
- 付属のMarkdown/TXTに加え、利用者が選択した文字レイヤー付きPDFを扱う。
- PDFはページ単位で抽出し、元PDFと抽出テキストを比較できるようにする。
- PDF抽出にはBSD-3-Clauseの`pypdf`を採用する。
- スキャンPDF、OCR、表・図、一般画像の意味解析は後続マイルストーンへ分離する。
- 個人進捗と実データは`.rag_lab/`へ保存し、Git対象外とする。
- UIは任意シェルを実行せず、定義済みPython関数だけを呼び出す。
- 自己実装とAI協働の両方を案内するが、コーディングAIをアプリから自動起動しない。
- 正式なUI起動コマンドは`rag-lab ui`、PDF取り込みCLIは`rag-lab ingest-pdf`とする。
- 対応範囲はPython 3.10から3.12、Windows、macOS、Linuxとする。
- UIは`127.0.0.1`だけで起動し、利用統計送信を無効にする。
- PDFは1件25 MB、200ページまでとし、暗号化されていない文字レイヤー付きPDFを正式対応とする。
- 実データ受け入れ試験では公開条件が明確な技術PDFを使うが、第三者PDF本体はリポジトリへ保存しない。

詳細な画面、アーキテクチャ、保存形式、テスト、受け入れ条件は`docs/LOCAL_LEARNING_APP_DESIGN.md`を正とする。

## 5. 学習ナビゲーションアプリに必要な体験

以下は製品要件として引き継ぐ。初期技術方式は4.5節のとおり決定済みであり、後続のOCR・画像対応は各段階の実装前に比較して決定する。

### 5.1 ホーム画面

- 全8 Labの一覧
- 未着手、進行中、完了、要復習の状態
- 現在の評価スコア
- 次に行う推奨タスク
- オフラインでできるLabと、AWSが必要なLabの区別

### 5.2 Lab画面

- このLabで学ぶ語句
- 実務で何に使うか
- 変更対象のファイル
- 実行コマンド
- 実行前に予想すること
- 出力のどこを観察するか
- 完了条件
- 発展課題

### 5.3 結果確認

- コマンドの成功・失敗
- 主要な標準出力
- 生成されたファイル
- 評価指標の変更前後
- 失敗した評価問題
- 期待値と実際の差

単に「成功」「失敗」を表示せず、なぜその結果になったかを学習者が考えられる情報を提示する。

### 5.4 問題診断

問題を少なくとも次に分類する。

- 環境構築: Python、仮想環境、依存関係、パス
- 文書加工: メタデータ、ページ、文字コード、チャンク
- Embedding: 次元、正規化、モデル不一致
- 検索: dense、BM25、hybrid、top-k
- 生成: 根拠不足、回答不能判定、引用
- 評価: ゴールドデータ、表記揺れ、指標の意味
- 外部API: 認証、モデルID、リージョン、タイムアウト
- AWS: IAM、ログ、費用、デプロイ

### 5.5 ヒント

ヒントは段階的に表示する。

1. 観察すべき場所だけを示す。
2. 原因候補を示す。
3. 関係するコードや設定を示す。
4. 最後に小さな修正例を示す。

最初から完成コードを表示し、学習機会を奪わない。

### 5.6 学習記録

最低限、次をローカルに保存できるようにする。

- 完了したLab
- 実行日時
- 使用した設定
- 評価値
- 問題点
- 仮説
- 実施した変更
- 結果
- 次に試すこと

個人の進捗、ページ抽出結果、チャンク、実行記録はdataset単位で`.rag_lab/`へ保存し、Git対象外とする。生PDFはデフォルトで保存せず、利用者が明示した場合だけ`.rag_lab/`へ保存する。公開可能なレポートは、利用者が内容を確認して明示的にエクスポートした場合だけ`reports/`へ出力する。詳細schemaは`docs/LOCAL_LEARNING_APP_DESIGN.md`を正とする。

同日、Streamlit 1.65.0と`streamlit-pdf` 2.1.0で`rag-lab ui`を実装した。AppTestで初期画面と付属データ経路を確認し、実サーバーが`http://127.0.0.1:8501`で起動してヘルスチェックへ応答することを確認した。利用統計送信は無効である。

公開実データ受け入れ試験では、NTRSで`Public`かつ`Work of the US Gov. Public Use Permitted.`と明記されたNASA Technical Memorandum 105232を使用した。PDF本体は一時領域だけで扱い、17ページから58チャンクを生成した。空ページと抽出警告は0件で、全チャンクの出典を保持した。1、9、17ページを画像と抽出テキストで比較し、帳票表のセル境界と読み順が完全には保持されない既知制約を記録したうえで`passed_with_limitations`と判定した。結果は`reports/lab1_public_pdf_acceptance_2026-10-03.md`にある。

同日、Lab 2の学習画面を追加した。付属データとLab 1保存datasetを選択でき、HashEmbeddingの次元、top-k、質問を固定してdense・BM25・hybridの順位を比較する。付属データでは回答可能な8問からHit@kを計算し、保存datasetではゴールド未設定であることを明示して目視評価する。run記録は`.rag_lab/runs/lab2/`へ本文なしで保存し、Lab 2進捗を更新する。

続けてLab 3の学習画面を追加した。同じdataset選択を再利用し、質問、検索方式、top-k、Embedding次元、回答可能性の予想を入力して、検索結果、抽出式回答、引用を段階表示する。回答時の引用追跡と回答不能時に引用を付けない規則を検査し、予想と実際が異なる例は`needs_review`にする。既知の回答不能誤判定を自動修正せず、観察教材として維持する。run記録は`.rag_lab/runs/lab3/`へ回答本文・チャンク本文なしで保存する。

## 8. 意図的に残している問題

初期実装は完成版ではない。次の問題はLab 6と7の教材として残している。

- HashEmbeddingは数値ベクトルの仕組みを学ぶためのベースラインであり、本格的な意味検索モデルではない。
- 抽出式生成器は似た単語があるだけで回答可能と判定する場合がある。
- 回答不能問題2件で誤回答があり、回答可能性判定は0.80である。
- 回答に必要な2文目ではなく、語が似ている別文を選ぶ場合がある。
- 要約は簡易的で、文書全体の重要度を高度に判断しない。
- プロンプト比較はBedrock等のLLMを接続しなければ十分に評価できない。
- FastAPIの検索・要約エンドポイントは未実装である。
- AWS SAMテンプレートは作成済みだが、SAM CLIによる実デプロイ検証はしていない。
- Lab 4以降の操作画面、詳細な問題診断、評価比較、公開レポート作成は未実装である。
- PDF取り込みは文字レイヤーだけに対応し、OCR、表構造、図、一般画像解析は未実装である。

これらを、説明なしに「不具合だから全部直す」のではなく、どれを教材として維持し、どれを学習アプリ側で案内するか区別すること。

## 10. 次の開発マイルストーン

### Milestone 0: 新規スレッドで現状を再確認

- この文書と関連ファイルを読む。
- ファイルツリーを確認する。
- テストと`rag-lab all`を再実行する。
- 文書記載と実装に差があれば、実装を証拠として差分を報告する。
- この段階では大規模な変更をしない。

### Milestone 1: ローカル学習アプリの方式決定

少なくとも以下を比較する。

- Streamlit等のローカルWeb UI
- FastAPIと軽量なフロントエンド
- PythonネイティブGUI
- CLIを維持し、TUIまたはHTMLレポートだけ追加

比較軸:

- 初学者の導入しやすさ
- Windows、macOS、Linux対応
- CLIとPython関数を再利用できるか
- 結果やグラフの見やすさ
- 任意コマンド実行を避けられるか
- テストのしやすさ
- GitHub配布のしやすさ
- 将来のAWS実習との分離

方式を決定する前にUI実装を始めない。決定理由を短い設計記録として残す。

## 11. 学習アプリの安全要件

- 任意のシェル文字列を利用者入力から実行しない。
- 実行できる処理は、定義済みのPython関数またはコマンドへ限定する。
- APIキー、AWS認証情報、個人情報を画面、レポート、Gitへ保存しない。
- `.env`をコミットしない。
- BedrockやAWSを使う前に、費用が発生し得ることを明示する。
- 文書中の命令文をアプリの命令として実行しない。
- エラー表示では、秘密情報を含み得る環境変数や完全な認証エラーをそのまま公開しない。
- 学習者のコードを勝手に上書きしない。変更を伴う操作は対象と差分を明示する。

## 12. 非目標

現段階では次を目標にしない。

- 大規模な商用RAGサービス
- 複数利用者のクラウドアカウント管理
- ブラウザ上での任意Pythonコード実行
- 実在する宇宙機の設計判断
- 学習者の代わりに全課題を自動実装するAI
- 高額な外部APIを前提にした学習経路
- eurosat-ai-labとのコード統合

`space-rag-lab`と`eurosat-ai-lab`は、目的とデータ種別が異なる独立プロジェクトとして扱う。

## 13. 新規スレッドで守る作業原則

- まず実装とテストを確認し、文書だけを信用しない。
- 既存の意図的な失敗を、学習目的を確認せず消さない。
- 1回の変更で複数の実験条件を同時に変えない。
- 振る舞いを変える場合はテストを追加または更新する。
- 変更後はテストと関連する評価を実行する。
- 大きなUI開発の前に、小さな縦切りでLab 1の体験を完成させる。
- 初学者向けの説明と、実務上の正確さを両立する。
- 重要な設計判断、現在状態、既知の問題をこの文書へ反映する。

## 14. 基本検証コマンド

プロジェクトルートで実行する。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
python -m unittest discover -s tests -v
rag-lab all
rag-lab ask "火星の砂嵐で太陽電池出力は何%まで低下しましたか？"
```

インストールせずに確認する場合:

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
PYTHONPATH=src python3 -m rag_lab.cli all
```
